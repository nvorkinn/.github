# Git workflow

- Never commit or push to main. Before making any change, create a new branch with a prefix: feature/, fix/, chore/, refactor/, test/, build/ or release/.
- Before starting, split the work into independent chunks. If two or more chunks don't touch the same files, start a separate cloud agent for each rather than doing them one after another. Keep related changes on the same agent to avoid conflicts. Agents you start follow these same instructions but must not start agents of their own without explicit consent.
- Running specific tests to check your work during development is fine. Don't run the full test suite as a final check before opening a PR, because CI runs it on the PR. Once the code is fairly final, commit, push and open the PR straight away.
- Open a PR in draft mode only if something manual has to happen before it can merge (e.g. a config change, a secret, or me doing something by hand). Take it out of draft once that's done. If a PR is only waiting on another PR, don't use draft. Stack it instead, using the `gh stack` extension (install with `gh extension install github/gh-stack` if missing) so GitHub recognises it as a proper stack. Don't just point the PR's base at another branch by hand.
- Watch the PR. React automatically to resolve git conflicts or failing CI. After every push check `mergeStateStatus`. If this comes back `CONFLICTING` or `DIRTY`, resolve problem immediately. If it comes back `UNKNOWN`, try again after a few seconds. Otherwise, start waiting for CI checks.
- Never sit idle waiting for CI. While a PR's checks run, carry on with the next piece of work. If the next step is independent, branch from origin/main after a fetch. If it builds on the waiting PR, create the next branch with `gh stack` so its PR is stacked on the waiting one.
- For local sessions:
  - Call `gh pr checks --watch <PR number>` in a background task to wait for CI to finish without burning turns. Retry if no checks are reported yet. Report the result (all checks pass/check failure) to the main task when the checks finish. If the PR is still open after the checks pass, start a second background task that calls `gh pr view --json state,mergeStateStatus <PR number>` every minute or so until the PR has merged or has conflicts, and reports that result (merged/conflict) to the main task.
  - If the background task reports either a check failure or conflict and the main checkout has moved on to another branch, resolve this in a temporary git worktree, which is removed afterward.
- For cloud sessions, watch the PR and react to events from GitHub itself while carrying on with other work. Even when all checks have succeeded, keep checking `mergeStateStatus` regularly until the PR is merged.
- Resolve git conflicts by merging the main branch into the dev branch instead of rebasing, as the latter requires a force push. Exception: branches in a stack managed by `gh stack` may be rebased and force-pushed by `gh stack` itself.
- When a PR is merged, delete the local dev branch. If we are not working on another change on another branch, switch back to main and pull (`git checkout main && git pull && git branch -D <branch>`). GitHub deletes the remote branch automatically on merge, so the local one is pointless. Don't discard uncommitted changes when switching.
- Don't start work until explicitly told to. For example, when asked a question, simply run the required analysis and answer the question - don't start making code changes.
